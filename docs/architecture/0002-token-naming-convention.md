# 0002 — Token naming convention

## Status

Accepted (stage 1 — foundations).

## Context

Goshi ships two product-mode namespaces, Consumer (`con`) and Enterprise
(`ent`), each with their own tokens, components and patterns, sharing a
common foundation. The brief specifies the convention by example:
`con.color.background.primary`, `ent.color.background.primary`,
`con.typography.heading.lg`, `ent.typography.heading.lg`.

## Decision

**Dot-path naming, mirrored 1:1 into a nested object structure.** A token's
name *is* its access path: `con.color.background.primary` in design docs is
literally `con.color.background.primary` in TypeScript
(`import { conByMode } from '@goshi/consumer-tokens'; conByMode.light.color.background.primary`).
There is no separate flattening/renaming step between "the token's name" and
"how you reach it in code."

### Path shape

```
<mode>.<category>.<...role segments>
```

- `<mode>` — `con` | `ent`. Chosen at the point where a package composes the
  final namespace (`@goshi/consumer-tokens`, `@goshi/enterprise-tokens`), not
  baked into `@goshi/foundations-tokens`, which is mode-agnostic.
- `<category>` — one of `color`, `spacing`, `sizing`, `radius`, `elevation`,
  `motion`, `typography`. Stable across `con`/`ent` (both have all seven
  categories — `ent.typography` is just empty right now, see ADR 0004).
- `<...role segments>` — semantic, not literal. `color.background.primary`
  describes *intent* ("the primary background"), never a colour name or hex
  value. See the semantic categories below.

### Semantic colour categories (fixed for stage 1)

`background`, `surface`, `text`, `border`, `icon`, `feedback.<danger|success|warning|info>.<background|foreground|border>`,
`interactive.primary.<default|hover|pressed|disabled|foreground>`. Defined
once in `@goshi/foundations-tokens`' semantic layer, aliased unchanged into
both `con.color.*` and `ent.color.*` (see ADR 0005).

### Primitive naming (not part of the public dot-path API)

Primitives (`color.blue.500`, `spacing.16`, …) are an internal
implementation detail of `@goshi/foundations-tokens` — semantic and
`con`/`ent` tokens reference them, but product code should not reach past
the semantic layer for colour (see ADR 0005's "escape hatch" note).
Scale categories (`spacing`, `sizing`, `radius`, `elevation`,
`motion.duration`, `motion.easing`) have no separate semantic layer — the
primitive scale step *is* the token (`con.spacing['16']`), since a spacing
value doesn't need an intent layer the way colour does.

### CSS custom properties

The same path becomes a kebab-case CSS custom property, prefixed `goshi`:
`con.color.background.primary` → `--goshi-con-color-background-primary`.
Generated by Style Dictionary's `css/variables` format (see ADR 0003) — no
separate naming decision to maintain, it falls out of the same source JSON.

## Consequences

- Renaming a semantic role (e.g. `text.tertiary` → `text.muted`) is a
  breaking change across `con`, `ent`, TS types, and generated CSS
  simultaneously — there's exactly one place the name is spelled
  (`packages/foundations/tokens/src/semantic/color.*.json`), so it can't
  drift, but it also can't be changed in just one output.
- Because the path *is* the API, adding a new semantic role requires adding
  it to both `alias.color.json` files (consumer and enterprise) even though
  only one platform might need it yet — there's no per-platform-only
  semantic token today. If that need arises, extend ADR 0005 rather than
  breaking the "semantics are shared" rule silently.
